# Gameplay Input and Visual Qualification

Gameplay shortcuts share `GameplayBindingRegistry` in the input boundary. The registry captures immutable keys, captions and cached English fallback prompts; the platform now recognizes every Latin letter. Camera mapping stays in the existing `RtsCameraBindings` contract and is consulted for conflicts. Selection, navigation and commands still use the existing presentation controllers and authoritative request gateway.

## Editing and migration

Open Settings from the main menu. Up/Down moves focus, Left/Right selects GAMEPLAY ACTION or changes GAMEPLAY KEY, and Enter/APPLY saves. The key row scrolls into the existing seven-row viewport. Pointer adjustment uses those same visible row identities. The editor shows each candidate, including a rejected candidate and its reason; rejection leaves the valid draft unchanged and disables APPLY. Move to another candidate or action to resolve it. A gameplay binding change uses the existing settings restart path before starting a match. ESC/BACK discards unsaved edits. Binding editing is a frontend workflow, not an in-match modal.

Twenty-five actions are configurable: seven dock modes, next item, two setting cycles, decrease/increase, activate/cancel job, base focus, formation, strategic layer, minimap, pause, five building shortcuts and placement rotation. Defaults remain B/P/U/L/Y/K/H, Tab/T/M/Left/Right/Enter/C, Home/F3/F10/F11/Space and F4–F9. Unknown/numeric undefined keys, duplicate actions, duplicate command keys, modifier keys, control-group digits and reserved help/developer/cancel keys are rejected. Assignment to a conflicting camera key is rejected for global actions. Dock-only keys intentionally replace camera navigation while the dock owns keyboard focus; global mode keys stay distinct from dock keys.

F1/F12 help, Escape cancellation/pause, mouse selection/targeting, Shift selection/repeat placement, Ctrl/digit group actions, modified developer/guide shortcuts and terminal R restart are fixed entries in the registry. They remain discoverable but are not arbitrary chord/mouse rebinding features. Camera drag and movement continue to use their existing settings.

Schema 1 migrates to schema 2 with default gameplay mappings and the saved camera/display values intact. Legacy camera mappings take priority over conflicting default global gameplay keys: the gameplay prompt says CAMERA KEY and that shortcut is suppressed until rebound. The saved camera is never rewritten to resolve a conflict. Invalid gameplay data alone is quarantined and recovered with an explanatory message while camera/display values survive. Malformed base settings retain the existing full-file quarantine/recovery policy. Settings application also preserves unrelated exposure/splash values.

## Prompts and feedback

Command cards, mode tabs, controls help, onboarding, placement/production explanations, hover hints, formation and map hints read the session registry. Captions and combined prompts are retained, not formatted during every HUD rebuild. The current UI language is English; the fallback prompt catalog is the shared source for key substitution, without claiming additional language packs. Supported Windows logical-key captions describe the key actually routed by the platform.

Contextual controls now use the same fill and shape policy as dock cards: hover outline, focus rail, pressed underline and disabled double rail. HOVER/FOCUS/PRESS text accompanies shortcut prompts, while disabled and pending controls retain the actual reason. Accepted/partial/rejected feedback continues to use authoritative result text and counts. Escape closing a panel displays CANCELLED - PANEL CLOSED for three seconds and submits no request. Targeting/placement cancellation retains its existing controls and preview clearing; local intent remains separate from accepted execution.

Short key taps are consumed once. Resize, session replacement, focus loss and help/modal suppression consume retained edges; held keys must be physically released before a fresh activation. Existing pointer ownership, minimap targeting, selection identity and intelligence masking remain intact.

## Automated fixtures and profiling

`GameplayUiFixtureTests` checks 135 command-surface combinations: 1024×720, 16:9, 16:10, ultrawide and 4K, 96/144/192 DPI, UI scale .75/1/2, long labels, focus/hover/press, missing materials, pending, accepted/rejected results and closed cancellation state. Checked-in vertex counts and SHA-256 geometry fixtures detect changes in positions, glyphs, colors and shape cues. Repeat rendering must match and all coordinates must remain finite inside the viewport. These are native renderer geometry contracts, not arbitrary-terrain contrast or screenshot acceptance.

Run the presentation tests normally to compare the checked-in fixture. For deliberate review, set `FORGELINE_UI_FIXTURE_BASELINE` to an explicit replacement file and `FORGELINE_UI_VISUAL_OUTPUT` to an explicit preview directory. Only reviewed replacements should enter source control. The latter exports SVGs built from the renderer's triangles; they exclude native textures, terrain and GPU rasterization. Clear those environment variables before validating the committed fixture. Existing display/minimap/intelligence and client journey suites remain gates.

Run `--gameplay-ui-hotpaths artifacts/gameplay-ui-hotpaths.json` through the Rendering benchmark host with `DOTNET_TieredCompilation=0`, restoring the prior environment value afterwards. The fixed compilation policy matches the alert/map qualification and does not change the client runtime. The 120 cases cross five display profiles, three scales, 1/1000 owned markers and four interaction states. After 128 warmups, 256 samples measure full HUD/input rebuilding, glyph vertices, managed allocation and actual vertex-data upload requests. Warm allocation must be zero. Requested upload bytes/calls describe the CPU submission payload; the null graphics backend does not time GPU transfers, driver waits or Present. CPU percentiles are observations, not portable timing limits. Existing interaction/hover/allocation checks remain unchanged.

## Native and manual acceptance

Run the repo-defined Release Windows window-mode qualification with 1,000 stress instances, isolated settings and the unchanged production asset report. Record actual viewport/DPI, submitted/presented frames, HUD vertices, binding failures, texture/descriptor lifetime budgets, optional debug-layer availability and whole-frame CPU/GPU timing. Whole-frame GPU milliseconds do not isolate HUD upload cost or establish steady-state FPS.

For manual acceptance, use the same deterministic match, camera/zoom and selected objects in windowed and borderless mode. Capture native screenshots for: normal and remapped controls help; keyboard-only Settings with a camera conflict; focused/hovered/pressed/disabled/pending cards; accepted/partial/rejected and local cancellation messages; operations and strategic-map overlays over bright terrain, dark vegetation and dense markers. Compare 16:9/16:10/ultrawide/4K, .75–2 UI scale, small viewports and long labels. Record screenshot names, build, real viewport/DPI, bindings, terrain and window mode alongside each image. SVG fixture previews do not replace this evidence.

Also exercise save/load/restart, alt-tab/held inputs, moving between monitors, help/pause, tactical/minimap capture and sustained high-load CPU/GPU/upload timings on the target refresh rates. Record failed or unexecuted items explicitly. No automated geometry or startup check alone qualifies these live monitor, terrain, framebuffer or performance acceptance items.
