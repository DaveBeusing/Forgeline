# World and Terrain

Terrain appearance continues to belong to Presentation and compiled material assets. Surface detail, slope-adaptive UVs, smoother blend regions and decorative plant motion do not change the authoritative heightfield, terrain normals, navigation, collision, concealment or intelligence. See [World Asset Presentation](WorldAssetPresentation.md) for authoring and [Bounded Terrain Surface Refinement](adr/BoundedTerrainSurfaceRefinement.md) for ownership and qualification.

## Purpose

`ForgeLine.World` owns the canonical spatial model and the first headless terrain representation for FORGELINE. Terrain rendering consumes this data through `ForgeLine.Presentation`; world state does not contain Direct3D 12 resources or presentation state.

## World Coordinate System

The canonical world convention is:

- world distances use meters
- +Y is up
- the ground plane is X/Z
- chunk coordinates are signed integer X/Z pairs
- chunk-local X/Z coordinates start at zero and increase toward the positive world axes
- conversion uses mathematical floor semantics, including negative world positions

A world position immediately below X=0 therefore belongs to chunk X=-1 rather than chunk X=0.

`WorldCoordinateConverter` is the canonical conversion boundary for world, chunk, region, and local chunk coordinates. Higher-level systems should reuse these contracts rather than define independent grid coordinate types.

## Chunk and Region Dimensions

The initial defaults are:

| Setting | Default |
| --- | ---: |
| Chunk size | 256 m × 256 m |
| Region size | 8 × 8 chunks |
| Height samples per chunk side | 65 |
| Terrain render vertices per chunk side | 33 |

Chunk size, region size, heightfield resolution, and render mesh resolution remain configurable.

The heightfield and render mesh intentionally use separate resolutions. World/simulation terrain data remains authoritative; presentation may render it at a different tessellation density.

## Heightfield Semantics

Each terrain chunk owns a square `TerrainHeightfield`.

Height samples:

- represent Y elevation in world meters
- include both chunk edges
- use a uniform spacing across the chunk
- are finite values
- are queryable without graphics initialization

`SampleHeight` performs bilinear interpolation at chunk-local X/Z coordinates.

`SampleNormal` derives an upward-facing normal from neighboring height samples. The query API is intended for later navigation, camera, placement, selection, and gameplay systems without introducing a rendering dependency.

The representative development terrain evaluates shared edge samples from canonical global sample coordinates. Adjacent chunks therefore produce identical height values on shared borders.

## Terrain World

`TerrainWorld` owns the current collection of `TerrainChunk` instances and exposes:

- deterministic chunk ordering
- coordinate lookup
- world bounds
- world-space height queries
- world-space normal queries

`ITerrainQuery` is the headless-facing query contract.

The first development map is generated by `DevelopmentTerrainFactory`. Its default radius is six chunks around the origin, producing a 13 × 13 chunk map large enough to exercise camera traversal, culling, and render submission.

The generated landscape combines broad hills, crossing ridges, and a basin. It is deterministic development data rather than a final art or map format.

## Terrain Mesh Generation

`TerrainMeshGenerator` converts one terrain chunk into presentation-ready CPU mesh data.

Each vertex contains:

- world-space position
- terrain normal
- chunk-local UV coordinates

Each quad is emitted as two indexed triangles. The current render resolution remains 33 × 33 vertices per chunk and can be changed independently of heightfield resolution. Terrain-albedo sampling therefore uses deliberately broad world-space tile scales so the authored variation remains readable at RTS camera distances without increasing terrain buffer density.

CPU mesh generation is deterministic for a given terrain chunk and mesh configuration.

## Rendering Ownership

Terrain rendering follows this ownership flow:

```text
ForgeLine.World
    terrain chunks + heightfields
        ↓
TerrainMeshGenerator
    CPU mesh data
        ↓
ForgeLine.Presentation.TerrainRenderer
    visibility + presentation resources
        ↓
ForgeLine.Graphics
    D3D12 buffers, pipeline, depth target, commands
```

The production `TerrainRenderer` prepares bounded GPU residency for the current camera/shadow union before recording. Chunk buffers and control textures are created on admission and reused while resident; eviction uses native fence retirement. Standalone construction without residency settings retains eager loading. See [World environment rendering](WorldEnvironmentRendering.md) for preparation, capacity failure and diagnostics.

The graphics layer owns native D3D12 resources and command submission. The world layer has no graphics reference.

## Material and Shader

The Vertical Slice terrain presentation defines eight stable material IDs for grass/ground, dirt, mud, rock, gravel, industrial ground, concrete, and scorched ground. Every P0 material resolves through the ordinary runtime material contract and provides Base Color, Normal, and ORM inputs. Missing optional channels retain the shared material fallbacks; source material or image files are never opened by the runtime.

Each terrain chunk derives a deterministic local palette of exactly four active materials from the eight-material library. `TerrainPresentationProfile.CalculateMaterialWeights` converts the existing Central Divide elevation, slope, and authored blend-region rules into explicit normalized material weights. `TerrainSplatMapBuilder` selects the four dominant materials for that chunk and generates a 33 x 33 RGBA control texture. Every texel is normalized to a byte sum of 255; invalid or zero weights select layer zero deterministically. The control texture carries a complete normalized mip chain.

The production D3D12 terrain shader binds one control texture plus four Base Color, four Normal, and four ORM textures. Base Color is blended with the control weights. Tangent-space normal samples are decoded, transformed against the terrain geometric basis, blended, and renormalized. ORM channels remain linear material data. The visual blend never becomes a gameplay terrain-classification input.

Terrain material UVs are calculated from world X/Z coordinates and a per-material tile scale. The world-space convention remains continuous across chunk boundaries and independent of screen resolution. Material textures use the shared anisotropic/trilinear wrap sampler and their compiler-generated mip chains; the control texture uses the shared linear clamp sampler. No negative global mip bias or forced highest-mip behavior is used.

Vertex color no longer contains final terrain albedo. The 48-byte terrain vertex keeps its color attribute only as a deterministic low-frequency macro/readability multiplier, leaving high-frequency Base Color and normal detail in tiled GPU textures. The macro multiplier combines two low-frequency world-space waves and is explicitly bounded to 0.90-1.08 so large terrain areas break up without producing high-contrast noise that competes with units or overlays.

The Central Divide readability baseline deliberately separates the eight material families by value as well as hue. Grass/vegetated ground remains the dominant natural mid-value surface; dirt and mud are warmer and darker; rock and gravel are lighter mineral families; industrial ground and concrete form a distinct constructed range; scorched ground remains the darkest family without using pure black. These values are presentation inputs only and never classify gameplay terrain.

## Frustum Culling

Chunk visibility is evaluated in presentation from the current RTS camera view-projection matrix.

`ViewFrustum` extracts six normalized planes using the Direct3D-compatible 0..1 depth convention and tests each chunk's world-space axis-aligned bounds.

Only intersecting chunks submit indexed draws.

Culling is intentionally chunk-level in this stage. Occlusion culling, hierarchical GPU culling, indirect execution, and finer-grained terrain visibility are deferred until measurements justify them.

## Debug Visualization

Development terrain rendering enables chunk debugging by default in the Windows client.

The terrain shader can:

- draw orange chunk borders;
- isolate each RGBA control channel;
- visualize the four selected palette material IDs.

Culled chunks are absent from submission, so movement through the world visibly exercises the culling boundary.

Runtime terrain diagnostics report:

- total, visible, and culled chunk counts;
- submitted triangle and draw-call counts;
- persistent terrain buffer and control-texture counts;
- the fixed texture-binding/sample budget per terrain draw;
- CPU terrain command-submission time.

The graphics diagnostics separately expose total resident texture bytes and SRV descriptor usage. Together these make material/descriptor growth observable without introducing per-frame descriptor allocation.

## Camera Traversal

The existing RTS camera remains presentation-owned.

The development client starts at a strategic zoom suitable for viewing multiple chunks and can pan continuously across positive and negative chunk boundaries. Camera movement changes visibility but does not mutate terrain/world state.

## Headless Use

World and terrain queries do not initialize:

- Direct3D
- a window
- input
- presentation
- UI
- audio

This keeps terrain usable by future navigation, building placement, selection, simulation, server experiments, and automated tests.

## Validation

Correctness coverage includes:

- positive and negative world-to-chunk conversion
- negative chunk-to-region conversion
- exact chunk boundary semantics
- height interpolation
- terrain normal sampling
- identical generated shared-edge heights
- headless world queries
- mesh topology and shared-edge positions
- frustum acceptance and rejection

The Windows client smoke path exercises actual terrain shader compilation, pipeline creation, depth-buffer creation, persistent terrain buffer upload, culling, indexed terrain submission, presentation, and orderly shutdown.

## Benchmarks

`ForgeLine.Rendering.Benchmarks` includes:

- terrain chunk CPU mesh generation
- visible terrain chunk render-submission preparation and command dispatch through a no-op graphics backend

Benchmark timing is measurement evidence and is not a hardware-sensitive CI pass/fail threshold.

## Canonical Vertical Slice operational geography

Central Divide is the canonical 3,072 m × 3,072 m Vertical Slice battlefield. Its terrain, Central Divide ridge, north/south crossings, expansion sites, resource locations, and static navigation obstacles are simulation-owned gameplay geography rather than presentation-only scenery.

Construction in the Vertical Slice now uses explicit map build zones instead of treating all world bounds as buildable. The owning start area, shared strategic sites, and bounded resource mining areas are buildable; unassigned terrain remains non-buildable while normal slope, collision, terrain, and resource-deposit validation still applies.

The canonical definition can be captured as a versioned `BattlefieldMapArtifact`. Map format version 2 records the terrain visual profile ID, RGBA four-layer control encoding, active-layer limit, control-map resolution, and the ordered eight-material library. It does not serialize renderer objects or make visual blend weights authoritative gameplay data. `ForgeLine.MapCompiler` compiles and reloads that artifact and runs headless operational-geography qualification before CI accepts the map. See [Strategic Map and Operational Geography](StrategicMapAndOperationalGeography.md).

## Vertical Slice presentation baseline

Central Divide now has a presentation layer above the simulation-owned chunked heightfield. Eight stable terrain material slots, nine reusable terrain texture sources, map-specific blend regions, reusable world objects, decals, and vegetation are defined without adding render material state to `TerrainWorld` or `TerrainChunk`.

Terrain GPU resources use compiled runtime materials and resident per-chunk geometry/control textures. A visible chunk submits one indexed draw with a fixed 13-texture binding budget. Central Divide retains all 144 CPU chunks; production GPU residency covers required chunks within its configured bound. Eager mode retains all 144 control textures at 33×33 plus mips. Material textures remain shared through the runtime cache. Props and vegetation use compiled assets, shared mesh buffers, distance-selected LODs and batched indexed instances. See [World Asset Presentation](WorldAssetPresentation.md) for authoring and [World environment rendering](WorldEnvironmentRendering.md) for residency and vegetation admission.

## Deterministic generation contracts

[Deterministic world generation](DeterministicWorldGeneration.md) defines the separate
versioned seed recipe, global integer sample lattice, independent domain sequences,
canonical gameplay/decoration identities and headless result boundary. These contracts
do not generate or replace the existing authored terrain recipes or compiled maps.

[Biome and ecology fields](BiomeAndEcologyFields.md) adds static, seed-controlled
temperature, moisture, soil suitability and softly weighted biome queries over the
unchanged ITerrainQuery. Immutable packed rasters expose headless distribution
diagnostics and bounded caching; rendering/scatter integration remains separate.

The opt-in [seeded landform factory](ProceduralTerrain.md) implements a separate
versioned height evaluator, flat/drainage masks and headless diagnostics on those
contracts. Existing authored maps continue to use their original recipes.


## Biome terrain materials

The opt-in [biome terrain material profile](BiomeTerrainMaterials.md) blends the existing
four-layer palette from environment fields and infrastructure masks. Authored renderer
defaults remain compatible; generated scenes explicitly select the new profile ID.
